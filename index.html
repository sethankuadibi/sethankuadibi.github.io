02 Approach — notes 03 notes

Built past the happy path.

Most demos stop at the first successful request. The interesting work starts at the second one.

  1. Note 01 — Failure

    Model the unhappy path first.

    Retries that land twice, spans that arrive out of order, a payment captured after a timeout. I design the failure cases before the happy path, because that is where trust is won or lost.

    ↳ modeled before the happy path

  2. Note 02 — Evidence

    Let the results pick the model.

    Baselines first, leakage checks, and reported numbers even when the simpler approach wins. In one MRI study the tuned SVM beat the CNN, and the write-up says so.

    ↳ the simpler model won

  3. Note 03 — Completion

    Finish the path through the interface.

    An API is not done until a person can use it. I stay for the empty state, the error message, the loading state, and the support question that follows.

    ↳ the API is not the product
